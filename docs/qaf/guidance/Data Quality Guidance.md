# Data Quality Guidance

This guide is a practical starter on how to approach data quality in our projects. It is not exhaustive and the nature of each project will call for a different focus.

As Data Scientists, Analysts or decision makers, data quality should sit at the core of everything we do with data models, insights and tools. We know that decisions are only as strong as the data they’re built on and so are the models.

The two tables below provide complementary perspectives on data quality. The first focuses on the **conceptual dimensions of data quality**, helping define what “good quality data” means and the types of issues that can arise. The second focuses on the **data science project lifecycle**, showing when and where these checks should be applied in practice. Considering both views is important while the dimensions help ensure that all aspects of data quality are covered, the lifecycle perspective helps embed these checks systematically throughout a project rather than treating data validation as a one-off step.

---

# **Checks by data quality dimension**

**Data quality is not a single validation step but a **continuous process embedded throughout the entire data science lifecycle**, from data acquisition to model monitoring in production.**

| **Data Quality Dimension** | **Description**                                                                                                                                                                                                                                                                    | **Data Quality Checks**                                                                                                                                                                                                                                                                                                     | **Examples**                                                                                                                                                                                                                                             |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Accuracy**               | Data correctly represents real-world values and reflects the truth. Look closely at each data field to see if the values look plausible, e.g. the height of a person recorded as 15 cm is clearly wrong.                                                                           | _ Range / threshold checks _ Outlier and anomaly detection \* Sudden drops / spikes in counts                                                                                                                                                                                                                               | _ Age must be between 0 and 120. _ Daily vaccination records suddenly drop from 20,000 to 500. \* A patient recorded as 1500 kg weight.                                                                                                                  |
| **Completeness**           | All required fields are populated and missingness is within acceptable thresholds, e.g. treatment information might only be populated for those receiving treatment.                                                                                                               | _ Null / missing value checks _ Mandatory field validation _ Missingness thresholds (warn / fail rules) _ Field-level coverage monitoring (e.g. provider counts)                                                                                                                                                            | _ NHS number cannot be null for patient records. _ Date of vaccination must be present if vaccinated_flag = TRUE. _ Missing ethnicity increases from 5% to 40% between months. _ Expected 100 GP practices submitting data but only 70 appear this week. |
| **Validity**               | The extent to which data conforms to the expected format, type, range and schema constraints.                                                                                                                                                                                      | _ Expected / needed data type checks _ Domain checks (allowed values) _ Regex / format validation (e.g. NHS number patterns) _ Detection of added, removed, or renamed columns (schema drift)                                                                                                                               | _ Age stored as integer not string. _ Gender must be in {Male, Female, Other, Unknown}. _ NHS number matches 10-digit checksum format. _ Pipeline fails because column `vaccination_date` renamed to `vaccine_date`.                                     |
| **Uniqueness**             | No unintended duplicate records; each entity appears once. Also, duplication exists when two records refer to the same entity (e.g. a patient) even if some of the data fields within those records, like post code or recorded ethnicity, do not match. These are harder to spot. | _ Duplicate row checks _ Apply business-key deduplication rules (your assumptions to dissambiguate)                                                                                                                                                                                                                         | _ Same NHS number + vaccination date appearing twice. _ Two records with same NHS number but slightly different postcode. \* Same patient + vaccine type + date recorded twice.                                                                          |
| **Integrity**              | Data does not contradict itself across systems, time, or fields. Relationships between datasets are correct and preserved.                                                                                                                                                         | _ Cross-field consistency checks (e.g., total = sum of parts, no male pregnancies) _ Referential integrity checks, (e.g. the first characters in a postcode should correspond to the locality of the address) _ Join consistency checks (detect orphan records) _ Distribution checks over time to detect unexpected shifts | _ No male pregnancies are recorded _ A patient is discharged before being admitted. _ A patient_id exists in vaccination table but not in patient table. _ Total vaccinations ≠ sum of regional vaccinations.                                            |
| **Timeliness**             | Data is available when expected and reflects the required time window. Some details can become outdated over time (e.g. old addresses or job titles).                                                                                                                              | _ Freshness checks (does the data corresponding to the period of interest) _ Detection of stale or outdated data (timestamp validation)                                                                                                                                                                                     | _ Conclusion for next year are made based on uptake probabilities from 10 years ago. _ Address last updated 15 years ago.                                                                                                                                |

# **Data Quality activities by Data Science project lifecycle**

Data quality isn’t a one-off task - it must be embedded at **every stage** of the DS lifecycle.

| **Stage in Data Science Lifecycle** | **Data Quality Activities**                                                                                                                                                                                              |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Data Scoping & Acquisition**      | Check source definitions, metadata, and business meaning. Validate the initial schema: data types, ranges, and required fields. Confirm data availability, refresh frequency, and known limitations.                     |
| **Data Ingestion & Preprocessing**  | Run automated checks for schema drift, nulls, duplicates, and invalid values. Apply transformations that enforce data types, formats, and ranges.                                                                        |
| **Exploratory Data Analysis (EDA)** | Look for unexpected patterns, outliers, spikes, and missingness. Check for distribution shifts or categorical imbalance. Validate assumptions about the data before modelling.                                           |
| **Feature Engineering**             | Ensure engineered variables reflect real business logic (e.g. dates, age ranges). Check for inconsistent derivations or faulty calculations. Check that new features behave consistently across time periods and groups. |
| **Model Training & Validation**     | Validate training / validation / test splits for representativeness.  Ensure no pipeline steps introduce new inconsistencies.                                                                                            |
| **Deployment & Monitoring**         | Monitor live data quality over time (key data quality metrics). Alert when production data violates expectations. Validate that model inputs remain within trained bounds.                                               |
