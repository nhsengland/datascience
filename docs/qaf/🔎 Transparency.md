# 🔎 Transparency

INLINE

*Transparency ensures that data science projects - during development, as well as final outputs - are open, explainable, and interpretable to stakeholders and end-users.*

**Success Criteria:** The project’s goals, methods, data, and outputs are presented in a way that is clear, accessible, and proportionate to the project’s impact.

* **RED:** Project outputs are opaque, with little explanation of how they were produced or what they mean.
* **AMBER:** Some elements of transparency are in place, but coverage is incomplete (e.g. methods explained but assumptions or risks missing).
* **GREEN:** Project is fully transparent with clear articulation of goals, data, methods, assumptions, limitations, risks, and outputs, using recognised formats (e.g. model cards).
* **NA:** Only where project outputs are entirely internal and exploratory, with no decision-making or wider use.

Transparency ensures that data science projects are open, explainable, and interpretable to stakeholders and end-users. It goes beyond documentation, requiring clear communication of goals, methods, data, and results so that decisions and outputs can be understood and trusted, including by those who may not have been involved in development cycle or have access to source data.

## Good Practice Guidance

| MSC | Good Practice |
| --- | --- |
| MUST | * **If** determined as in scope by the Business Critical Models Oversight Group, the model is included in the organisation's Business Critical Analysis Register. See [Model Quality Assurance and Business Critical Models](./templates/Model%20Quality%20Assurance%20and%20Business%20Critical%20Models.md) for guidance |
| MUST | * Provide a plain-English summary of the purpose of project outputs, what they should and should not be used for, and any other important caveats - to be routinely shared alongside other dissemination of project outputs. |
| SHOULD | * Project goals, intended outcomes, and planned approaches are shared openly (e.g. on the data science website) during development. |
| SHOULD | * Transparency materials (such as codebase, model card) are made available alongside any [Comms & Marketing](./%F0%9F%93%A3%20Communication%20%26%20Marketing.md) activity. |
| SHOULD | * If appropriate, the model / system is reported on via the [Algorithmic Transparency Recording Standard Hub](https://www.gov.uk/government/collections/algorithmic-transparency-recording-standard-hub). |
| SHOULD | * Adopt standard approaches to sharing summary information about model / system for public consumption - such as publishing a [Model Card](https://nhsd-confluence.digital.nhs.uk/spaces/DAT/pages/749482620/Ethics+Hub#EthicsHub-%F0%9F%97%82%EF%B8%8FModelcards). |
| SHOULD | * Transparency materials (e.g. model cards, reports) cover assumptions, limitations, risks, and potential biases. |
| SHOULD | * Codebase is published in the open (GitHub). |
| COULD | * Adopt 'coding in the open' practices - such as working from an open GitHub repo during development. |
